# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-user, local-only desktop app that tracks which tickets were worked on with AI assistance. It scans Claude Code session transcripts (and accepts manual entries), infers ticket keys, enriches them from JIRA or ClickUp (read-only), and visualizes the relations with charts. Photino.NET host (.NET 10) + OS-native WebView + vanilla-JS frontend + SQLite. No server, no team sync, no Electron.

Licensed under MIT (`LICENSE`); third-party notices for vendored JS and NuGet deps are in `THIRD-PARTY-NOTICES.md`.

## Commands

```bash
dotnet run                              # launch the app (Photino window)
dotnet build                            # build only
dotnet run -- --scan                    # headless: run the transcript scanner, print counts
dotnet run -- --sql "SELECT ..."        # headless: read-only query (PRAGMA query_only=ON enforced)
dotnet run -- --set <key> <value>       # headless: write a Settings row (use jira_token / clickup_token for the DPAPI-protected tokens)
dotnet run -- --route <page>            # open the app directly on a page (dashboard|sessions|manual|tickets|livecode|settings) — used for headless UI verification; also accepts a param, e.g. --route "session/<sessionId>" for the session detail page
dotnet run -- --detailtest <sessionId>  # headless: print the session-detail deep re-parse (per-tool/per-model/timing), as fed to the detail page
dotnet run -- --pty-test                # headless: spawn a pseudo-console and verify continuous output streaming (Live Code terminal)
dotnet run -- --envtest                 # headless: verify ANTHROPIC_API_KEY is stripped from a session's child env
dotnet run -- --shelltest               # headless: print resolved PowerShell / Git Bash executables
dotnet run -- --accounttest             # headless: print subscription plan + usage-reset date from ~/.claude.json
dotnet run -- --usagetest               # headless: print the Live Code usage-limit bars (Platform/ClaudeUsage)
dotnet run -- --clickuptest <key>       # headless: fetch one ClickUp task by key and print it
dotnet run -- --version                 # headless: print the stamped semver + git commit + build date

# Publish the single-file, self-contained exe (see PROGRESS.md for the deliverable path):
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true -p:DebugType=none -p:DebugSymbols=false
```

Unit tests live in **`AIUsage.Tests/`** (xUnit) — run with **`dotnet test AIUsage.Tests`**. They cover
the pure-logic core (transcript aggregation, ticket-key inference, context-window sizing, the XLSX
writer) plus the data layer (migrations + repositories against an in-memory SQLite DB). The suite is
deliberately **not** wired into a `.sln` (a solution would make the bare `dotnet run`/`dotnet build`
at the repo root ambiguous); root commands still target the single app csproj, and the app project
excludes `AIUsage.Tests\**` from its compile glob (the test folder is nested inside it). Beyond the
tests, UI/integration verification is still done via the `--scan`/`--sql`/`--route`/`--pty-test`/`--envtest`
CLI verbs and window screenshots.

Packages: Photino.NET, Microsoft.Data.Sqlite, System.Security.Cryptography.ProtectedData, SQLitePCLRaw.bundle_e_sqlite3, **Porta.Pty** (ConPTY wrapper for the Live Code terminal; managed-only, so the single-file publish is unaffected).

## Architecture

**Message bridge.** The WebView and .NET communicate over Photino's string message bus as JSON. Request `{ id, action, payload }` → response `{ id, ok, data | error }`. `Bridge/MessageRouter.cs` parses, dispatches by `action` to a registered handler on a pool thread, and serializes the reply (camelCase). Frontend side is `wwwroot/js/bridge.js` — `Bridge.call(action, payload, timeoutMs)` returns a Promise; pass `timeoutMs: 0` for unbounded operations (e.g. JIRA sync, Excel export) so the client doesn't strand a still-running backend call.

The bridge also has an **unsolicited event channel** for streaming (used by the Live Code terminal): `MessageRouter.PushEvent(event, data)` sends `{ type:"event", event, data }` with no request id, and the frontend subscribes via `Bridge.on(event, handler)`. Regular request/response is unchanged.

**Handlers** live in `Bridge/Handlers/*.cs`, each with a static `Register(router)` called from `Program.cs`. **Critical trap** (documented in `SessionHandlers.Register`): synchronous handlers must run inline and return `Task.FromResult<object?>(...)`. Do NOT wrap the body in `Task.Run(() => { ...; return null; })` — it binds to the `Func<Task<object?>>` unwrap overload, and unwrapping a null task yields a *canceled* task, surfacing as a spurious "A task was canceled" error even though the DB write committed. `MessageRouter.OnMessage` already provides the pool thread.

**App version.** `AIUsage.csproj`'s `<Version>` is the single semver source of truth (bumped by hand). A `SetGitCommitHash` MSBuild target runs `git rev-parse --short=7 HEAD` best-effort and sets `SourceRevisionId`, which the SDK appends as `+<hash>` onto `AssemblyInformationalVersion`; an `AssemblyMetadata` item stamps the UTC build date. `Platform/AppVersion.cs` reads both back at runtime (`Semver`, `Commit`, `BuildDate`, `Short`, `Detail`) — everything else (the `app.info` bridge action, the `--version` CLI verb, the sidebar footer) reads from this one class. A build made outside a git checkout just omits the commit; nothing fails.

**Scanner pipeline** (`Scanner/`): `TranscriptScanner` walks `%USERPROFILE%\.claude\projects\**\*.jsonl` (append-only JSONL), incrementally by remembered byte offset (`ScanState` table); it reads only complete lines (stops before a partial trailing line a writer may still be appending) and uses `BEGIN IMMEDIATE` transactions so concurrent scanners (even other processes) don't double-count. Counters are **additive** across incremental parses; a shrunk/rewritten file triggers a full reparse that first zeroes counters. → `SessionAggregator` is the **ONLY** place that knows the undocumented Claude Code transcript schema — put all format-drift fixes here; unknown/malformed lines are skipped, never fatal. → `TicketKeyInferrer` extracts ticket keys with source priority **branch → cwd → prompt_text**, filtered by a project-key allowlist. Sidechain/subagent transcripts (in session-named subdirs) are skipped in v1. Alongside the token counters, the scanner also refreshes each changed file's **`ToolUsage`** rows — per-session sub-agent / skill / MCP-server / hook counts from a full-file parse (`SessionAggregator.ReadToolUsage` → `ToolUsageRepo.ReplaceForFile`, **set** semantics, decoupled from the incremental token counting). This powers the dashboard's **Automation & extensions** charts (`stats.dashboard` → `agentUsage`/`skillUsage`/`mcpUsage`/`hookUsage`). The v6 migration flags a one-time backfill (`toolusage_backfill_pending`) so sessions scanned before this table existed get populated on the next scan. The scanner also writes **`SessionDailyTokens`** — the same additive in/out counters split by the **local calendar day** each message was sent (`SessionAggregate.DailyTokens`, keyed via `SessionAggregator.LocalDay` → `SessionDailyRepo.Accumulate`, zeroed by `DeleteForFile` alongside `ResetCountersForFile` on a full reparse). A Claude Code session routinely spans days, so `Sessions.started_at` can't carry any windowed figure; these buckets are what the Live Code "last 7 days" tile sums (`SessionDailyRepo.RollingTokens`). The v7 migration flags `dailytokens_backfill_pending` for a one-time full re-derivation (`BackfillDailyTokens`, **replace** semantics so it's safe over files the incremental loop already accumulated). The dashboard's **Token usage per week** chart reads these buckets too (`StatsHandlers.TokensWeeklySql`), falling back to a session's `started_at` week only for sessions with no buckets.

**Data layer** (`Data/`): raw ADO.NET via `Microsoft.Data.Sqlite`, no ORM. `Db.Open()` sets WAL + foreign_keys. `Migrations.cs` is idempotent (`CREATE TABLE IF NOT EXISTS` + `AddColumnIfMissing` for post-ship columns), seeds `ActivityCategories`, and stamps `SchemaVersion` (currently 8; v8 added `Tickets.provider`, backfilled `'jira'` for previously-synced rows). Repositories in `Data/Repositories/`. **DB location is portable-first**: `aiusage.db` next to the exe when that dir is writable (so the whole folder is copyable), falling back to `%APPDATA%\AIUsage\` only under Program Files; an existing %APPDATA% DB is copied over once (with `-wal`/`-shm`).

**Frontend** (`wwwroot/`): classic scripts + globals — **no ES modules** (they don't load over `file://` in WebView2). `app.js` is a hashchange router; each view self-registers on `window.Views` (`window.Views.<name> = ...`) and exposes `render(container, param)`. The hash may carry one param after the first `/` — `#session/<id>` routes to the `session` view with `param = <id>`; the router maps the `session` route back to the "Sessions" sidebar item for highlighting. The **Sessions list → detail** flow uses this: each row title links to `#session/<id>`, and `session.js` renders a detail page (Overview / Tools / Models / **Agents & extensions** / Token cost / Tickets) from `sessions.detail`, which re-parses that one transcript on demand (`SessionAggregator.ReadDetail`) for the exact per-tool + per-model breakdown, reply/tool-call counts, an Agent/Active/Idle time split, and the sub-agents/skills/hooks used (agents ← Agent/Task `subagent_type`, skills ← Skill `skill`, hooks ← `hook_success`/`hook_error` attachment lines, MCP tools ← the `mcp__…` tool names) — none of which the list/DB stores; token **cost** is derived in the view from a per-model-version `$/Mtok` rate table (`rateFor` in `session.js`: family + the lowest model version each price applies to, because Anthropic re-prices within a family — Opus went 15/75 to 5/25 at 4.5; `<synthetic>` turns are free and unrecognised ids price as current Opus). Shared helpers live on `window.App` (`toast`, `esc`, `fmtNum`, `fmtDate`, `refresh`, `exportExcel`). Chart.js is **vendored** at `wwwroot/lib/chart.umd.js` (no CDN — corporate network blocks it and the app runs offline). Dashboard charts use a fixed category→color palette (color follows the activity category, not its rank). The **Non-ticket sessions** chart (between Top tickets and Ticket type × AI activity) is the counterpart to Top tickets: `stats.dashboard` → `nonTicketProjects` (`StatsHandlers.NonTicketProjectsSql`) sums sessions with **no** `SessionTicketLinks` row per project folder — grouped case-insensitively, since transcripts record the same Windows folder as both `C:\…` and `c:\…`.

**Embedded web assets** (`WebAssets.cs`): `wwwroot/**` is compiled in as embedded resources (`LogicalName=web/...`) so the published exe is one self-contained file. On startup they're extracted to `%LOCALAPPDATA%\AIUsage\web` and loaded over `file://` (keeps `crypto.randomUUID` working). **Extraction overwrites on every launch**, so editing `wwwroot` and re-running (or re-launching the exe) picks up changes. Dev fallback: on-disk `wwwroot` next to the exe if no embedded resources.

**Ticket trackers** (`Tickets/`, `Jira/`, `ClickUp/`): tickets are enriched read-only from JIRA and/or ClickUp behind one abstraction, `Tickets/ITicketProvider` (`FetchAsync`/`AssignedAsync`, plus `Id`/`DisplayName`/`ItemNoun`), so callers (bridge handlers, Live Code) never branch on which tracker owns a key. `Tickets/TicketProviders.ProviderIdFor(key)` routes a key from **config alone, no network**: a ClickUp **native** key (a bare task id with no dash, e.g. `86b1abcde` — exactly the id ClickUp itself shows, `Data/TicketKey.IsClickUpNative`) always routes to ClickUp; otherwise the key's project prefix is checked against the `clickup_custom_id_prefixes` setting (ClickUp **Custom Task IDs**, e.g. `DEV-123`, configured per-workspace in ClickUp) and only routes to ClickUp if listed; everything else routes to JIRA. `.For(key)`/`.Enabled()` additionally gate on `jira_enabled`/`clickup_enabled` and whether that tracker's client is configured, returning null/empty rather than throwing (enrichment is optional). `Tickets/TicketSync` (provider-neutral; replaces the old `Jira/JiraSync.cs`) is the fire-and-forget enrichment fired on link creation, and `Tickets/TicketInfo` is the provider-neutral row both trackers map onto (`Provider`, `IssueType`, `Project`, `Sprint`, `IsDone`, `PriorityRank`, …). `PriorityRank` (0 = highest) orders the Live Code picker ahead of recency; JIRA tickets are all rank 0 (today's pure-recency behavior, unaffected), while `ClickUpTicketProvider.RankAndFilter` keeps only tasks in a fixed ClickUp status priority (In Progress → PR Initiated → Planned → Open) and assigns each its tier — any other status (Testing, Documentation, Done, Closed, …) is excluded from the picker entirely, not just deprioritized.

JIRA (`Jira/JiraClient.cs`): read-only JIRA Cloud REST. Token is DPAPI-protected at rest (`SettingsStore.SetProtected`, `dpapi:` prefix; non-Windows falls back to `plain:`) and write-only in the UI. The DPAPI token does NOT survive copying the folder to another machine/user — it degrades to "not set" by design. **Never paste a real JIRA token into Claude** — use `--set jira_token` or the Settings UI. `FetchIssueAsync` also fetches the description and flattens the ADF (Atlassian Document Format) tree to plain text. The **site URL is validated, not just trimmed** (`Jira/JiraSiteUrl.cs`): absolute `https://`, real host, no `user:pass@` — because the Basic header is a *reversible* credential and `http://` sent it in cleartext. Every writer validates (`settings.set`, `--set jira_site_url`), `JiraClient.FromSettings()` returns null for an insecure stored value (so a legacy/hand-edited setting disables JIRA instead of leaking), `settings.get` exposes `jiraSiteUrlInsecure` so the Settings page explains it, and **pointing the URL at a different host clears the stored token** so it can't be replayed to a new server.

ClickUp (`ClickUp/ClickUpClient.cs`): read-only ClickUp REST v2, using a personal API token (`pk_…`) sent raw in the `Authorization` header (https://developer.clickup.com/docs/authentication#personal-token) — DPAPI-protected at rest (`clickup_token`) and write-only in the UI, same treatment as the JIRA token. **The host (`https://api.clickup.com/api/v2`) is a compile-time constant, not a setting** — unlike JIRA there is no user-supplied base URL, by design, so the token can never be sent to another host or over `http://`. **Never paste a real ClickUp token into Claude** — use `--set clickup_token` or the Settings UI. A task is fetched by native id, or by Custom Task ID once a workspace (`clickup_team_id`) is set (`custom_task_ids=true&team_id=…`); `clickup.test` verifies the token, lists workspaces, and auto-fills `clickup_team_id` when there's exactly one. `ClickUpClient.IsNotFound` also treats ClickUp's `ECODE: ITEM_*` 401/400 bodies as "not found" (its API returns those instead of a clean 404 for a dead/foreign task) — this mapping is an educated guess from the ClickUp docs, not yet confirmed against a live workspace (see PROGRESS.md open items).

**Live Code page** (`Terminal/`, `Bridge/Handlers/LiveCodeHandlers.cs`, `wwwroot/js/views/livecode.js`): interactive Claude Code sessions embedded in the app — **multiple concurrent sessions, one per UI tab**. Each tab is identified by a frontend-minted `tabId` (a GUID, stable across the tab's Stop→Resume/Reset), and the backend keeps a `Dictionary<tabId, LiveSession>` (replacing the old singleton). `ConPtySession` hosts a shell in a pseudo-console — via the **Porta.Pty** library, NOT raw ConPTY: a hand-rolled `CreatePseudoConsole` implementation ran the child fine but conhost wouldn't stream output continuously on this Windows build (only flushed on resize/close), so we use the library (see PROGRESS.md). Output bytes stream to the WebView over the event channel as `pty.output` (each event tagged with its `tabId`) and render in **xterm.js** (vendored at `wwwroot/lib/xterm.*`, same no-CDN constraint as Chart.js); one xterm per tab, all in a persistent container with only the active tab shown, and a single subscription routes events by `tabId`. Keystrokes go back via `pty.input` (also carrying `tabId`). Every per-session action (`start`/`resume`/`reset`/`stop`/`closeTab`/`attach`/`metrics`, `pty.*`) requires a `tabId`. On start, the chosen shell (`ShellResolver`: PowerShell, or Git Bash with fallback) is spawned in the selected folder, then a `claude …` command is *typed in* to work the selected ticket (built by **`Terminal/ClaudeCommand.cs`** — `BuildTicket`/`BuildResume`/`BuildResumeSession` — flattened to one line, sanitized, and shell-quoted; see the gotcha below, this seam is where remote JIRA/ClickUp text becomes a shell command line and it is the one place in the app that has had a HIGH-severity injection bug). `BuildTicket` takes a closed-set `TrackerLabel` enum (`Jira`/`ClickUp`), never a fetched string, to name the tracker in the kickoff sentence ("JIRA ticket …" vs "ClickUp task …") — so no remote data can reach that label. A supplied ticket key is validated (`Data/TicketKey.Require`) before anything launches. `ANTHROPIC_API_KEY` is stripped so Claude Code uses subscription auth (Porta.Pty inherits the parent env and ignores dict removal, so `ConPtySession` also unsets the var in this process). Confirmations: `--permission-mode acceptEdits` (auto-approve) or `bypassPermissions`, plus a best-effort `PromptWatcher` that injects Enter on detected prompts. **The elevated modes are granted by the host, not the page**: the checkbox only *requests* one, and `GrantPermissionMode` shows a **native** OS Yes/No dialog (`Platform/MessageDialog.cs`, UI-thread-marshalled like `FolderDialog`) once per tab per mode. Denied, or no window (headless), or a dialog failure → the mode is dropped and the session runs with normal prompts; the result carries `permissionMode`/`permissionRequested`/`permissionDenied` so the page toasts and unticks the box. This is why launch calls must use `Bridge.call(…, 0)`: the handler blocks on a human. Do NOT reintroduce a frontend-only confirm for these modes — the point is that a script in the WebView cannot answer the dialog. Starting a session with a ticket **auto-links** it (`SessionRepo.LinkLiveCodeSession`, source `livecode`) so the work is captured. On open, the page checks the CLI is installed (`Terminal/ClaudeCli`) and warns if not. The shared ticket picker at the top lists the user's most-recently-updated assigned tickets **merged across every enabled tracker** (finished statuses excluded), newest-first by parsed instant (`LiveCodeHandlers.OrderByUpdatedDesc`/`ParseUpdated` — JIRA's no-colon offset and ClickUp's UTC `…Z` format don't compare correctly as raw strings, so ordinal string sort must never be used to merge the two lists); how many it shows is configurable in **Settings → Live Code** (`livecode_ticket_count`, default 3, clamped 1–20; surfaced to the page via `livecode.config`'s `ticketCount`, alongside `ticketsConfigured`/`ticketProviders` — whether any tracker is enabled + configured, and which), and a **↻ Re-fetch** button beside the list reloads them from every enabled tracker on demand (`livecode.tickets` queries them concurrently; one tracker's failure is reported per-tracker in `errors` rather than blanking the other's results). ClickUp tickets are additionally filtered and ranked by status before recency (`ClickUpTicketProvider.RankAndFilter`, `TicketInfo.PriorityRank`): only **In Progress → PR Initiated → Planned → Open** status tickets are eligible at all (everything else — Testing, Documentation, Done, Closed, … — never reaches the picker, regardless of how recently it was touched), and within the merged list a lower-numbered rank always outranks a higher one even if the higher-ranked ticket is more recently updated; recency is only the tiebreak within the same rank (`LiveCodeHandlers.MergeForPicker`). JIRA tickets are unaffected — all rank 0, same pure-recency behavior as before. Agents: the dropdown lists `.claude/agents` (project + user); a **Custom Agent** file picker installs a chosen `.md` into `.claude/agents` and the kickoff becomes "Use the &lt;agent&gt; agent to work on &lt;ticket&gt;" (prompt-based, no `--agent`). Selecting an Agent from the dropdown clears + disables the Custom Agent input (the two are mutually exclusive; `refreshControlLocks` is the single locking authority). A **Resume Sessions** button (beside Browse) lists the chosen folder's existing Claude Code sessions (`livecode.sessionsInFolder` → `Scanner/FolderSessions.cs`, labelled by each transcript's first user prompt via `SessionAggregator.FirstUserPrompt`); picking one resumes it interactively (`livecode.resumeSession` → `claude --resume <id>`, no prompt) in the active tab (confirm-replace if running) and locks Shell/Model/Custom Agent until it stops. The button is disabled when the folder has no sessions. Each tab has its own compact "this session" tokens/context readout (`livecode.metrics {tabId}`, polled for the active tab); the session **Tokens** figure is `input + output` **including sub-agents** — the SAME formula as the dashboard and `weekTokens` (so the numbers stay consistent across the app), just with sub-agent usage added. Cache is shown **separately** as a **Cache** field (`cache_creation + cache_read`, with a "created … · read …" tooltip) so it never inflates the headline Tokens number. Task-tool sub-agents write to `<sessionId>/subagents/agent-*.jsonl` sidechains that the scanner skips, so `SessionAggregator.SubagentTokens` returns their in+out and cache split (`SubagentUsage`) and the handler adds both (Tokens returned split as `mainTokens`/`agentTokens`; cache as `cacheTokens`/`cacheCreation`/`cacheRead`). The sub-agent re-add is display-only for this readout — the DB/dashboard/`weekTokens` still exclude cache and sub-agents (v1 design). The dashboard and `weekTokens` count `input + output` only (all cache excluded). `weekTokens` is a **rolling last-7-days** sum over `SessionDailyTokens` (`SessionDailyRepo.RollingTokens(conn, 7)`), matching the WEEK usage bar beside it — NOT sessions grouped by `started_at`'s calendar week, which credited a multi-day session's whole spend to the week it began in and so collapsed the tile to near-zero every Monday. The shared bottom panel keeps the plan, week tokens, a **variable set of rolling usage-limit bars**, and the top-5 active Claude Code sessions (`Scanner/ActiveSessions`). The bars come from `Platform/ClaudeUsage.cs` → `livecode.usage`: a GET to Anthropic's `oauth/usage` endpoint (the same data as Claude Code's `/usage`), authed with the access token from `~/.claude/.credentials.json` (token used only to sign the request, never stored/logged). Rather than fixed SESSION/WEEK fields, `ClaudeUsage.Bars` is an ordered list built from whichever windows the endpoint returns for the seat: `five_hour` (SESSION), `seven_day` (WEEK), and, for Max/Team seats with per-model caps, `seven_day_opus`/`seven_day_sonnet`; an `extra_usage` block becomes its own bar labelled **MONTHLY LIMIT** when it's the *only* window present (an Enterprise spend-capped seat has no rolling 5h/7d windows at all — confirmed against a live Enterprise seat probe, 2026-09) or **EXTRA USAGE** when it supplements the rolling windows (top-up credits alongside a Pro/Max/Team seat), with a `$used / $limit` detail string from the endpoint's `used_credits`/`monthly_limit`/`decimal_places`/`currency`. Percents are server-computed (no local quota math); unrecognised/codenamed windows are ignored rather than guessed at. Cached 5 min and best-effort (bars hide when signed out/offline); the page polls every 60s and colours a bar amber ≥80% / red ≥95%. `Platform/ClaudeAccount.cs`'s plan label follows the same "don't guess" rule: a zero/none rate tier contributes no tier label (so an Enterprise seat with a flat spend cap shows plainly as "Enterprise", not "Enterprise · Zero"), and a `planLimitsEndDate` already in the past is hidden rather than shown stale. Tabs (and their sessions) survive navigation: `tabs[]` lives in the view closure, `ConPtySession` keeps a per-tab rolling output buffer, and on return the page reconciles with `livecode.list` and `livecode.attach {tabId}` replays each running tab's buffer into a fresh xterm (the router wipes the DOM but not the backend sessions). **Stop** (`livecode.stop {tabId}`) kills the process tree but keeps the entry so Resume works; **closing a tab** (`livecode.closeTab {tabId}`, confirmed if running) disposes and drops the entry; **Resume** re-launches `claude --resume <id> 'continue'`; **Reset** sends `/exit` then restarts a fresh Claude session on the same ticket (shared `StartTicketSession`). New tabs inherit last-used defaults; soft cap of 6. The sidebar dot (app.js polls `livecode.running` → `{running,count}`) is green when any session runs, red when none; hovering the nav item shows a popover listing live tabs (`livecode.list`), and clicking a row focuses that tab. The active-sessions list polls a scan-free `livecode.activeSessions` every 2s. **Same-folder safeguard**: on Start, if another running tab is already working in the chosen folder, the page shows a warning (concurrent agents on one folder can corrupt edits — "own risk") with a git-repo-aware 3-way choice (`App.choose`): **isolated worktree** / continue in same folder / cancel. Choosing worktree passes `isolation:"worktree"` to the backend, which runs `GitWorktree.Create` (`Terminal/GitWorktree.cs`) — a new branch `livecode/<ticket>-<hex>` in a sibling `<repo>-worktrees/…` folder — and launches the session there (transcript + auto-link use the worktree cwd; `livecode.folderInfo` reports whether a folder is a git repo). Reset reuses the tab's worktree; **closing** a worktree tab removes it only if clean (`TryRemoveIfClean`: no uncommitted changes and no unmerged commits), else keeps it. Isolated tabs show a `⑂` marker.

## Conventions & gotchas

- **`net10.0`**, nullable + implicit usings enabled. Namespaces mirror folders (`AIUsage.Bridge.Handlers`, etc.).
- Ticket keys are validated via the single shared **`Data/TicketKey`** (`IsValid`/`Normalize`/`Require`), which every writer of `SessionTicketLinks.ticket_key` goes through, including inside `SessionRepo` itself — do NOT re-declare either regex in a new handler. Two grammars, told apart by dash presence alone (JIRA/Custom Task ID keys always have one, a raw ClickUp id never does — no invented prefix): JIRA-style `^[A-Z][A-Z0-9]{1,9}-\d{1,6}\z` (uppercased on normalize), and ClickUp **native** `^(?=[0-9a-z]*[a-z])(?=[0-9a-z]*[0-9])[0-9a-z]{6,12}\z` — a bare task id exactly as ClickUp itself shows it (its task URL, "Copy ID"), lowercase body kept as-is since the id is case-sensitive in the ClickUp API. Both anchor with `\z`, not `$` — .NET's `$` also matches before a trailing `\n`, and a key ending in a newline would become an Enter keystroke when typed into the Live Code shell. The ClickUp pattern requires the id contain **both a letter and a digit**, so an ordinary lowercase word (a branch segment like `hotfix`) never passes as a task id, and a JIRA project literally named `CU` (`CU-123456`, digits only after the dash) still parses as a JIRA key, not a ClickUp one. A ClickUp native key has no project part (`TicketKey.ProjectOf` returns null for any dash-less key), so the project allowlist never applies to it — it's always kept by the allowlist purge. Auto-links carry a `source`; manual/confirmed links are preserved when the allowlist purge runs (`SettingsHandlers.PurgeDisallowedAutoLinks`), whose effective allowlist is the user's `project_key_allowlist` **∪** the enabled `clickup_custom_id_prefixes` (`SettingsStore.EffectiveKeyAllowlist`; an empty user allowlist stays empty — "allow everything").
- **The Live Code command line is TYPED into a shell, so quoting alone is not enough.** All untrusted text (JIRA summary/description, agent names) must go through `ClaudeCommand.Quote`, which sanitizes first: PowerShell terminates a single-quoted string on **any** of `U+0027 U+2018 U+2019 U+201A U+201B`, so a smart apostrophe pasted from Word/Outlook into a ticket used to break out and execute; and because the line is delivered as *keystrokes*, control bytes are consumed by the shell's line editor (0x15 kills the line, 0x03 cancels it, 0x1B reverts it) one layer *below* the parser that quoting protects. `Sanitize` folds the Unicode quote classes to ASCII and drops every control character. Never concatenate fetched JIRA text into a command line without it, and keep the length caps.
- **No inline `onclick="…"` handlers with interpolated values.** `App.esc` is an HTML-text escaper; an event-handler attribute is entity-decoded during HTML tokenization and only *then* compiled as JS, so `&#39;` arrives at the compiler as a live apostrophe and closes the string. Use `data-*` attributes plus a delegated listener (`Views.sessions.bindActions` is the pattern, shared by the Sessions list and detail pages; `app.js`/`livecode.js` do the same).
- Headline token figures **exclude cache-read tokens** by design.
- Anything windowed by time (per-week charts, rolling totals) must come from **`SessionDailyTokens`**, not `Sessions.started_at` — a session routinely spans days, so `started_at` attribution silently moves large amounts of spend into the wrong bucket. Likewise, order session lists by `COALESCE(ended_at, started_at)`: a resumed session keeps its original `started_at`.
- A security decision the backend acts on must not be made in the WebView: the bridge dispatches by action name with no origin check, so any script in the document can call any action with any payload. Confirmations that only gate UX belong in `App.confirm`; anything that grants a *capability* (today: the Live Code permission modes) goes through a native host dialog. `SendWebMessage` posts asynchronously, so a native modal never blocks PTY output or other handlers.
- Do NOT use Photino `ShowSaveFile` off the UI thread — it returns null (reports a false "cancelled"). Excel export (`Export/XlsxWriter.cs`, minimal hand-rolled OOXML, no new dependency) saves directly to Downloads and reveals via `explorer /select`.
- The startup background scan only re-renders the input-free dashboard, never a view the user may be typing into (re-render wipes form state via `innerHTML`).
- **ConPTY streaming**: use `Porta.Pty`, not raw `CreatePseudoConsole` — the raw path doesn't stream continuously on this machine (see the Live Code paragraph). Stripping a child env var also unsets it in the app process (Porta.Pty inherits parent env); only `ANTHROPIC_API_KEY` is stripped today, which the app never reads.
- Claude Code encodes a session's cwd into its `~/.claude/projects/<name>` folder by replacing `:`, `\`, `/` with `-`. Live Code launches `claude --session-id <guid>` so `FindActiveTranscript` reads exactly `<guid>.jsonl` — matching by "newest file in the dir" is wrong because other concurrent Claude Code sessions (even this one) write to the same folder.
- Git Bash is resolved from the Git-for-Windows install paths, **never** a bare `bash.exe` on PATH — on Windows that's `C:\Windows\System32\bash.exe` (the WSL launcher), which fails with `execvpe(/bin/bash)` when there's no distro (`ShellResolver.IsSystemShim`).

## Screen Capture & Window Access

- **NEVER** capture the screen programmatically from PowerShell/.NET. Do not use `System.Drawing` `CopyFromScreen`, `System.Windows.Forms` screen grabs, or `Graphics.FromImage`/`Bitmap.Save` to screenshot the desktop or any application window.
- **NEVER** use `Add-Type -TypeDefinition` to compile inline C# that P/Invokes `user32.dll`/`gdi32.dll` — e.g. `EnumWindows`, `GetWindowRect`, `GetWindowText`, `GetWindowThreadProcessId`, `MoveWindow`. Do not enumerate, locate, resize, or capture the windows of other processes.
- **NEVER** reflectively load .NET assemblies in memory to interact with the screen, windows, or input devices.
- If you need to see the UI to verify a change, **ASK the user to take a screenshot and paste it in**, or use the application's own built-in screenshot / export / replay feature. Do not script the capture.
- Do not write captured images to `%TEMP%`, the Claude scratchpad, or anywhere else as a workaround for asking the user.

Context: In-memory `System.Drawing`/`CopyFromScreen` screen capture and Win32 window enumeration launched from `powershell.exe` trigger Microsoft Defender "Suspicious screen capture activity" (Collection; AMSI + Behavior). See INC0035079 / INC0035085 — part of the Claude/EDR false-positive family under INC0034383.
